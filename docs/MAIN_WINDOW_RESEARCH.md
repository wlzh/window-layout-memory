# 通用主窗口识别：验证阶段

## 首次授权采样结果（2026-09-12）

用户随后打开图片窗口后，同一微信进程暴露4个窗口，92次读取、无截断。新增三按钮窗口（关闭/全屏/最小化）AXMain=true；原三按钮窗口AXMain=false，另有两个两按钮窗口。全部仍无窗口标识、标准类型且父级为应用。两个三按钮窗口仅全屏按钮下AXGroup的深度不同，尚无稳定性证据，不能作为可靠身份。此反例排除了“仅凭全屏按钮或AXMain认主窗口”的方案；未读取图片内容或更改规则。当前证据支持研究按应用隔离的允许名单，但微信无标识时仍需固定主窗口标题等额外约束，跨重启识别尚未验证。

用户打开子窗口后的同进程复测：微信暴露3个窗口，均AXWindow/AXStandardWindow、parentRole=AXApplication、AXModal=false，均无窗口标识。一个窗口含关闭/全屏/最小化3个按钮，另外两个只含关闭/最小化2个按钮；两按钮窗口之一AXMain=true，三按钮窗口AXMain=false。采样66次读取，无截断。由此不能使用AXMain作为固定主窗口身份，也不能用父级应用区分主子窗口。当前按钮差异只是候选特征，不足以证明所有子窗口或重启后仍可区分。诊断未读取标题，未将窗口序号当作持久身份。

诊断进程已授权，真实只读采样通过。微信当前暴露1个标准窗口，无窗口标识，只有3个标题栏按钮；另一微信实例当前没有可读取窗口。Arc当前1个窗口提供非空标识（仅记录哈希），但跨重启稳定性未知。Chrome与ChatGPT当前窗口均无窗口标识，在深度3范围内角色结构相同（不同应用可由bundle隔离，尚不能证明同应用窗口之间可区分）。WPS当前窗口含33个直接子元素，触发每层16个的采样限制，结果标为截断，不能据此认定身份唯一。

以上窗口的parentRole均为AXApplication，当前均AXMain=true。这只是当前单窗口状态，不是主/子窗口分辨成功。未退出或重启任何应用，未改布局和例外；下一步需要同一应用同时存在已知主窗口及子窗口，再比较它们的特征，随后由用户确认是否做关闭重建及重启验证。

此阶段不改现有铺满策略、不删除例外、不重装正式应用。目标是评估每个应用可指定多个允许窗口并跨重启识别，未知窗口默认不处理；不能把系统AXMain状态等同于持久的产品主窗口。

一次性诊断工具：`scripts/window-identity-probe.swift`。编译为独立可执行文件后，传入目标bundle标识。无窗口写操作、激活、观察者或常驻任务，不读标题、正文、描述、路径和截图；标识只输出SHA256以便比较。最多12个窗口，每窗口64个结构节点、深度3、每层16个子节点；全局600次属性读取及5秒软截止，每次AX消息超时80ms。超时或截断不作为完整身份依据。

该独立进程需要辅助功能权限，已安装主程序的授权不自动共享。`--self-test`仅验证哈希，不代表真实AX测试。未获权限时退出2并明确报告，不返回伪造的空窗口成功结果。

采样矩阵：微信主窗口/群聊/记录/图片、浏览器主窗口/设置/独立窗口、文档应用主窗口/文档/对话框。比较同次运行切换、关闭重建、应用重启前后结构与标识。应用重启应由用户确认，防止影响未保存工作。进程号、窗口序号、焦点状态均不可作为持久身份。

结论门禁：同应用中唯一、跨重启稳定、主/子窗口不存在冲突才允许自动认回；结构相同或信息缺失时不能猜测。完成验证前保留全部原例外，版本维持已安装preview.19 / build 26，不宣称主窗口白名单已经实现。
